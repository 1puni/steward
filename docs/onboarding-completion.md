# Completing an organisational steward installation

A successful requested task proves a reactive work path. An organisational
steward expected to drive work forward also needs a way to select useful next
work, revisit external waits, change its operating schedule and report verified
outcomes. Establish the intended operating model from the user's existing
instructions; do not silently substitute a reactive assistant or import another
instance's personal procedures.

## Establish the installed capability

Read the running revision, effective configuration, installed drivers and owning
world instructions. Record each needed capability as supported and observed,
configured but unverified, missing installation, missing implementation, or
deliberately excluded by the user's scope. A package containing a scheduler is
not an installed schedule. A YAML file in a repository is not an installed
configuration update path. Native task tools vary by revision: a missing argument
or unreadable protected file does not establish a harness-wide limitation.

Protected configuration and delegated configuration changes are compatible.
A steward may prepare versioned policy while a trusted installer applies only
authorized changes after validation. Identify the actual publication, installation,
restart, observation and rollback steps. Do not claim per-field delegation unless
an installed boundary enforces it. Schema validation alone is not an authority
allowlist. Preserve credentials and host control outside model execution.

## Prove the requested operating model

For a proactive organisational stewardship, retain evidence for these outcomes:

| Outcome | Acceptance evidence |
| --- | --- |
| Useful work advances unattended | A bounded next step toward an accepted priority is selected, admitted and completed through the installed task path, with the resulting publication or external effect verified. |
| External waits resume | A temporary observer has a completion condition, bounded cadence, durable evidence and a single reconciled notification intent; it fires without another operator message. |
| Scheduling has a lifecycle | The steward creates, adjusts and retires a harmless schedule through its authorized configuration path. Observe the installed values and final absence, including after restart. A perpetual no-op is not removal. |
| Publication checks establish something useful | Repository-specific checks reject a representative bad candidate and accept its repair. Whitespace-only gates do not establish application, dataset or research correctness. |
| Deployment and rollback work | The exact published revision is observed at its target, and an isolated unhealthy-release exercise verifies rollback without risking unrelated services. |
| Recovery survives loss of cognition | A separate installed health mechanism detects a controller failure and exercises its permitted recovery or alert route. A procedure inside the failed controller cannot supply this guarantee. |
| Authority remains bounded | Out-of-scope configuration, repository and credential operations are rejected. Routine work already authorized by the user does not prompt again. |

Use harmless fixtures and existing authorized work. Do not purchase, message third
parties, manufacture business objectives or widen account access to fill a table.
If the installed revision cannot supply a requested outcome, finish the concrete
source/configuration handoff and identify the specific remaining installation or
grant. The installation is partial until the required evidence exists; a running
service and one deployed task are not substitutes.

## Leave an operable stewardship

The owning world should tell the steward where its priorities live, how to discover
capabilities, which configuration source it can change, how those changes become
effective, what gates and limits apply, and how to distinguish a genuine external
dependency from missing knowledge. Link implementation details to their owning
repository. Record intentional instance differences and their reasons.

Keep one versioned source of configuration truth. If a one-time installer leaves a
repository template stale while live configuration evolves, reconcile that source
before enabling automatic installation. Otherwise the first self-deployment can
quietly remove fixes made during onboarding.
